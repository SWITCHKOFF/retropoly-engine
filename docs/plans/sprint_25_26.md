## Задачи

**Неделя 49 — Архитектура и синхронизация:**

- [ ] [B] Определить разделение работ: Master — main loop/игровая логика/backend; Slave — параллельный workload (кандидат: подготовка вершин/command list). Не закреплять VDP1 за Slave как «аппаратное правило» — разделение software-defined
- [ ] [B] `scu_sync`: обёртки над SCU-прерываниями, семафорами и барьерами; таймауты и диагностика, без бесконечного busy-wait
- [ ] [B] Карта shared-памяти в WRAM-L/WRAM-H: выравнивание, владение, read/write-контракты; учесть кэш SH-2 и явные flush/invalidate
- [ ] [B] ADR-009: dual-CPU partitioning, протокол синхронизации, ответственность Master/Slave, fallback
- [ ] [B] Схема жизненного цикла: boot Slave → handshake → работа → stop; повторный запуск и ошибка загрузки Slave

**Неделя 50 — Slave worker и очередь:**

- [ ] [B] `slave_worker.cpp`: загрузка/запуск Slave, idle-loop, обработка команд, корректная остановка; без динамических аллокаций
- [ ] [B] Fixed-size SPSC ring queue: атомарные индексы, memory barriers, детерминированный порядок; переполнение — `false` + диагностика
- [ ] [B] Master dispatch API: постановка job, ожидание completion, таймаут, fallback на single-CPU
- [ ] [B] Host-тестируемая логика очереди (unit-тесты) + smoke-тест в эмуляторе
- [ ] [B] Метрики: счётчики busy/idle для Master/Slave, количество job, время ожидания

**Неделя 51 — Интеграция параллельного workload:**

- [ ] [B] Распараллелить один реальный workload (трансформация/клиппинг или подготовка command list) за compile-time/runtime-переключателем
- [ ] [B] Сравнить single-CPU и dual-CPU: корректность кадра, frame time, загрузка CPU; зафиксировать baseline
- [ ] [B] Синхронизация с VBlank: Slave не пишет в VRAM вне разрешённого окна; отсутствие tearing/race
- [ ] [B] `docs/benchmarks/saturn_reference_environment.yaml`: версия эмулятора, настройки, CPU utilization, frame time, git_revision
- [ ] [B] Диагностика: переполнение очереди, timeout, повторный job, остановка Slave — без крашей

**Неделя 52 — Стресс и гейт:**

- [ ] [B] 10-минутный стресс в pinned-эмуляторе: отсутствие deadlock/hang, стабильный frame time
- [ ] [B] Детерминизм: повторный прогон с одинаковым вводом даёт одинаковый кадр/хэш
- [ ] [B] Fault injection: Slave не стартовал, Slave завис, очередь переполнена — Master продолжает работу в fallback
- [ ] [B] CI: `build-saturn.yml` зелёный; артефакт образа; PC/PS1 не регрессировали
- [ ] [B] Документация: `docs/SATURN.md` (разделение работ, sync, ограничения), CHANGELOG

## Критерии приёмки спринта 25–26

- [ ] Оба SH-2 реально используются; это подтверждено счётчиками/профайлером, а не только фактом запуска Slave
- [ ] Параллельный workload даёт измеримый прирост на выбранной задаче; порог и методика зафиксированы в ADR-009
- [ ] Повторный прогон детерминирован; race/deadlock не воспроизводятся в 10-минутном стрессе
- [ ] При отказе Slave Master продолжает работать в single-CPU fallback без краша
- [ ] VBlank-синхронизация не даёт tearing; PC/PS1 тесты зелёные

## Риски

- **Гонки и когерентность кэша.** Митигация: явные барьеры/flush, минимум shared-состояния, host-тесты очереди, стресс.
- **Дисбаланс Master/Slave.** Митигация: начать с одной workload, мерить, не усложнять до измеримого выигрыша.
- **Тайминги эмулятора.** Митигация: pinned-эмулятор, фиксированные настройки, отдельный baseline; не обещать real-hardware performance.
- **Сложность отладки.** Митигация: счётчики, debug-лог, fallback-режим, минимум параллельного кода в v0.2.0.
